1. P1 — CANCELLED QUEUED INVESTIGATION RESTARTS
Source: apps/api/recovery_api/investigate.py:run_investigation (around569),
_persist_conclusion (around298), and routes.py:cancel.
Reproduction: create another investigation; cancel before processing its queued
job; process jobs. Expected incident OPEN with cancelled run; observed incident
AWAITING_APPROVAL. run_investigation only skips COMPLETED, then overwrites CANCELLED
with RUNNING. _persist_conclusion does not revalidate cancellation/active run under
a lock before creating another open proposal. That new proposal can become eligible
for approval because the cancelled run remains the active investigation.
Fix: validate run lifecycle/incident active run at job start AND before persistence;
make cancel/supersede durable and race-safe. Cancel or invalidate pending jobs, but
do not rely only on queue cancellation because a worker may already be executing.
Test cancellation before job start and during tool/model execution; test an old
queued investigation completing after a newer run. Assert no fresh actionable
proposal is published and no cancelled run becomes RUNNING/AWAITING_APPROVAL.

2. P2 — RETRIEVED RUNBOOK CONTENT STILL NOT SENT TO MODEL
Source: apps/api/recovery_api/agent.py:scoped_observation (around35);
investigate.py:_apply_tool search_runbooks branch.
Customer record evidence now reaches the model, which fixes the original major
defect. However search_runbooks produces runbook_text and evidence IDs, while
scoped_observation sends only IDs. A probe with a harmless reconnect instruction
confirmed that none of its text is visible to the model. The model cannot learn
the actual operating procedure from this tool.
Fix: send bounded sanitized retrieved documents with IDs, titles, versions and
content, marked untrusted. Preserve tool/write restrictions instead of deleting
all content. Implement validated query/limit arguments if adaptive search is claimed.
Test real retrieved text in the exact provider payload, malicious text treated as
data, valid citations, and retrieval relevance.

3. P2 — BUDGET CHECKS CAN BE BYPASSED BY THE FINAL RESPONSE
Source: apps/api/recovery_api/agent.py:run_model_loop (around107–165),
llm.py:OpenAICompatibleCompleter, routes.py:investigate budget construction.
Checks happen before a provider call. The code aggregates returned usage and can
immediately accept a diagnosis without checking usage/time again. Probe: max_tokens
10, a final diagnosis reporting10000tokens; returned model success, no budget error.
The same applies to final-call elapsed time/cost. No provider output-token ceiling
is sent. Cost enforcement is disabled after a provider omits price, without a
configured conservative estimate. The route also hardcodes a0.05budget overriding
the configured cost setting. These are soft accounting checks, not a hard spend cap.
Fix: validate positive budgets; honor configured ceilings; recheck usage/time after
every call and before acceptance; bound response tokens and remaining HTTP timeout
where supported. Estimate cost using explicit model rates or label cost unknown and
require a bounded explicit policy. Do not imply rejecting a result refunds usage
already consumed. Test final-call overrun and unknown/invalid/negative usage values.

4. P2 — LIVE EVALUATION EXECUTION IS STILL NOT WIRED
Source: evaluations/run_baseline.py and evaluations/runners.py:live_status (216).
The single-pass/tool-agent contract runners now genuinely execute with fake
completers, which is useful. But CIR_EVAL_LIVE=1 plus credentials only changes
live_status to configured. The main runner always scores weak_contract_completer
and weak_tool_completer; it never constructs the live adapter or evaluates it.
This is an implementation gap beyond simply missing credentials.
Fix: add an explicit opt-in live command constructing the configured provider and
running both approaches on a bounded selected split. No automatic paid calls.
Test wiring with an injected provider, then run actual evaluations only after Vinay
authorizes provider credentials/budget. Label live/fake outputs accurately.
Also tool_agent currently receives the full case observation before requesting
tools, and every tool returns the full observation. This cannot establish that
adaptive evidence collection helps. Use tool-specific observations from a hidden
case environment with the same repair policy and clearly documented evidence
availability for both approaches.
